Expected output of `gudprobe` against blitsCRT_Mister, with no arguments.

Generated on Linux by running the probe tool's own dump code against the
device's device.c in the loopback harness -- so this is what the exe prints,
not an approximation of it. Regenerate with `make golden`.

If what comes out on Windows differs from this, the difference is the finding.
The two worth checking before anything else:

  magic   anything but 0x1d50614d means this is not a GUD interface. On a
          MiSTer board the likeliest cause is the USB hub add-on still fitted,
          which reaches the same dwc2 controller.

  flags   STATUS_ON_SET must be present. Without it every failed modeset from
          here on silently looks like a success.

A mode count of 4 with wrong numbers in it means the wire structures are being
padded -- but the static asserts in include/gud.h should have stopped that at
compile time, so check they were not compiled out.
